# OneLake Medallion

[![ci](https://github.com/Shiva-data101/OneLake-Medallion/actions/workflows/ci.yml/badge.svg)](https://github.com/Shiva-data101/OneLake-Medallion/actions/workflows/ci.yml)

I built a local lakehouse on the Olist Brazilian e-commerce dataset. Daily landing files go into append-only bronze Delta. dbt builds silver and gold on DuckDB. A quality gate sits on top (`dbt_expectations` plus Soda Core), and GitHub Actions blocks a bad merge.

I am now lifting the same project to Fabric and OneLake. Terraform is still later.

## Get the data

The raw CSVs are not in git. Download the public [Brazilian E-Commerce Public Dataset by Olist](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce) from Kaggle. Unzip all nine CSVs into `archive/` at the repo root.

```text
archive/
  olist_customers_dataset.csv
  olist_geolocation_dataset.csv
  olist_order_items_dataset.csv
  olist_order_payments_dataset.csv
  olist_order_reviews_dataset.csv
  olist_orders_dataset.csv
  olist_products_dataset.csv
  olist_sellers_dataset.csv
  product_category_name_translation.csv
```

`data/landing/`, `data/bronze/`, and the DuckDB file are generated by the scripts below. I do not commit those either.

## How it is wired

```text
archive/ CSV  ->  generate_batches.py --cutoff  ->  data/landing/YYYY-MM-DD/*.parquet
                                                data/landing/_meta.json
                                                data/landing/_reference/*.parquet
                     reset.py                  ->  empty bronze, watermarks, run_log, duckdb
                     ingest.py --backfill      ->  bronze through cutoff
                     dbt build (full)          ->  staging / silver / gold + 61 tests
                     replay_days.py --days 30  ->  ingest --once + incremental dbt, 30 times
                     run_soda.py               ->  freshness and row-count contracts
```

## Three clocks

I keep three clocks and I do not mix them. Mixing them is how I lost a full replay once.

Landing folder date is when the order was placed. `generate_batches.py` writes `data/landing/YYYY-MM-DD/`. That is a source-arrival simulation, not a watermark. A late update of an old order still lands in a new folder, with a newer `updated_at`.

The ingest folder cursor is `last_batch_date` in `data/control/watermarks.json`. Ingest only opens folders after this date. After `--backfill` through `2018-06-30`, the cursor sits on the last backfill folder. `--once` then takes the next folder, which is the replay queue. This cursor never reads row contents.

The dbt watermark is `_ingested_at` on the table already built. On later runs, incremental models keep rows where `_ingested_at > max(_ingested_at)` on `{{ this }}`. I stamp that column at ingest time, so it only moves when a batch is written. `is_incremental()` is false on the first build. `unique_key` plus `delete+insert` replaces a late update of the same business key instead of duplicating it.

I do not watermark dbt on `order_date`. A late update of an old order would be dropped. I also do not watermark on `updated_at`. That is a business lifecycle time, and after backfill it already sits in the future. The diagnosis is below.

Cutoff is inclusive. `order_date <= 2018-06-30` is one backfill load. Later folders are the replay queue. The cutoff lives in `data/landing/_meta.json`. Folders stay flat (`landing/YYYY-MM-DD`).

## Tools

Use Python 3.12 or 3.13. This repo is pinned to 3.12. Stable dbt does not run on 3.14.

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\dbt.exe deps --project-dir transform --profiles-dir transform
```

Quality checks are dbt generic tests, `dbt_expectations` 0.10.10, and Soda Core v4 (`soda-duckdb`). I tried Soda Core v3 (`soda-core-duckdb` 3.5) first. It pins `duckdb<1.1` and cannot run against this warehouse (DuckDB 1.5.5). You do not need Azure CLI, Terraform, Docker, or a Fabric trial to run the local path.

Pull-request CI is under [CI (Phase 3)](#ci-phase-3).

## Run the cutoff + 30-day replay

From the repo root:

```powershell
.\.venv\Scripts\python.exe scripts\generate_batches.py --cutoff 2018-06-30
.\.venv\Scripts\python.exe scripts\reset.py
.\.venv\Scripts\python.exe scripts\ingest.py --backfill
.\.venv\Scripts\python.exe scripts\run_dbt.py --run-type full
.\.venv\Scripts\python.exe scripts\replay_days.py --days 30
.\.venv\Scripts\python.exe scripts\run_soda.py
```

`reset.py` is safe to run again. It deletes bronze, `watermarks.json`, `run_log.jsonl`, and the DuckDB file. It leaves `landing/` and `archive/` alone.

If `landing/_meta.json` exists, a bare `ingest.py` is refused. Pass `--backfill`, `--once`, or `--all`. I did this so I cannot ingest the replay queue by accident.

To inject a late-arriving row (old `order_date`, new `updated_at`, new landing folder):

```powershell
.\.venv\Scripts\python.exe scripts\generate_batches.py --cutoff 2018-06-30 --inject-late
```

## Gold models

`dim_customer` is one row per `customer_unique_id`. Olist reissues `customer_id` on every order, so the person key is `customer_unique_id`. `dim_product` is `product_id`. `dim_date` is calendar day. `fct_order_items` is `order_id` + `order_item_id` and it is incremental. `fct_daily_sales` is one row per order date.

Source files are `data/control/run_log.jsonl` and `data/benchmark/replay_days.jsonl`. The Phase 2 `dbt build --full-refresh` line is from the same `run_log.jsonl` after I added the quality gate (`duration_seconds` 12.262, dbt reported 8.10s).

### What went wrong

The first 30-day replay proved the folder cursor was correct and the dbt watermark column was not. Each July day appended to bronze (`order_items` 98,309 → 105,024). `fct_order_items` stayed at 98,309 with `max(order_date)=2018-06-30`.

I had written the incremental predicate as `updated_at > max(updated_at)`. `updated_at` is the latest business timestamp on the row (delivery, shipping limit, estimated delivery). After backfill, `max(updated_at)` on silver orders was already `2018-10-17` and on items `2020-04-09`. Every July purchase looked older than that watermark and was dropped.

So I changed the watermark to `_ingested_at`. That column is stamped when the file hits bronze. It only moves when ingest runs. After the same 30-day replay with that change, July rows land in gold (`max(order_date)=2018-07-30`, 6,715 July fact rows).

## Data quality gate

`dbt build` now runs 23 models and 61 tests. It prints 84 because it counts both together. I set every bound from the warehouse after the 30-day replay. I did not guess. I also did not add a test that the model already filters, because that test can never fail.

### Prove it fails

Staging only `try_cast`s `review_score`, so a 99 would reach silver and pull average rating. The named gate is `dbt_expectations.expect_column_values_to_be_between` on `silver_order_reviews.review_score` (1–5).

```powershell
.\.venv\Scripts\python.exe scripts\prove_quality_gate.py
```

I measured this on this machine. Bronze review `a8724d975e573edc200c3e34515b8e83` was copied with `review_score=99` and a new `_ingested_at`. Incremental `dbt build --select silver_order_reviews` failed:

`dbt_expectations_expect_column_values_to_be_between_silver_order_reviews_review_score__5__1` → **FAIL 1**.

I then appended the same `review_id` with the original score `5`. The same test **PASS**ed. Bronze stays append-only. Silver `delete+insert` on `review_id` keeps the latest arrival.

### What the dbt tests protect

On `silver_orders`, `unique` and `not_null` on `order_id` stop a double-counted or missing order from flowing into items and payments. `not_null` on `customer_id` matters because `dim_customer` is keyed on `customer_unique_id` and joined through this id. An order with no customer vanishes from person-level revenue. A null `order_date` cannot join `dim_date` or land in `fct_daily_sales`, so that day's GMV disappears. `accepted_values` on `order_status` drops junk like `unknown` from delivered and canceled filters. `expect_column_distinct_count_to_be_greater_than` on `order_status` > 1 catches a load that collapsed every order to one status. Mix charts would still look fine. The real mix would be gone. `expect_column_pair` checks delivered ≥ purchase. A delivery before purchase inverts SLA and days to deliver. Freshness is `expect_row_values_to_have_recent_data` on `silver_orders._ingested_at` (7 days). If ingest has not written, silver is stale even if `order_date` still looks like 2018. I put freshness on arrival time, not order date.

On `silver_order_items`, `unique` and `not_null` on `order_item_key` stop duplicate lines from inflating item count and revenue. `order_id` must exist on `silver_orders` because gold inner-joins items to orders. An orphan item never reaches `fct_order_items`, so category revenue is understated. The same pattern holds for `product_id` → `silver_products` and `seller_id` → `silver_sellers`. An orphan `product_id` fails the `dim_product` join and silently drops that category. An item with no seller cannot be attributed. `order_item_id` is between 1 and 30. A 0 or 999 is a parse error that would invent extra lines. Measured max after replay was 21. `price` ≤ 15000 on rows that are not quarantined. A million-real glitch would dominate daily revenue and AOV. Negatives are quarantined on purpose, so they are not in this test. Measured max after replay was 6735. `freight_value` is 0–2000 on the same rows. Measured max after replay was 409.68.

On `silver_order_payments`, `unique` and `not_null` on `payment_key` stop duplicate sequences from double-counting cash. A payment with no order is cash that never shows on the purchase. `accepted_values` on `payment_type` drops a typo from the credit-card vs boleto mix. `payment_value` is 0–20000. A negative shrinks GMV. A huge one spikes it. Measured max after replay was 13664.08. `payment_installments` is 0–24. 36+ is not an Olist plan. Measured max after replay was 24.

On `silver_order_reviews`, a duplicate `review_id` inflates average rating. A review with no order cannot be tied to a purchase. A null `review_score` is dropped from the average. The 1–5 bound is the named gate in `prove_quality_gate.py`. A score of 99 pulls CSAT up. The mean is also bounded (3.5–4.7). A flood of all-1s or all-5s moves CSAT even when every row is still in 1–5. Measured mean after replay was 4.076.

On the other silver tables: `customer_id` is the per-order customer key. Duplicates fan out joins into `dim_customer`. Without `customer_unique_id` I cannot count repeat buyers, because Olist reissues `customer_id` per order. A junk UF such as `XX` on `customer_state` breaks regional GMV. Duplicate `product_id` duplicates `dim_product` and fans out facts. `product_weight_g` is 0–50000. A negative weight is a unit error. A 200 kg phone would skew shipping models. Measured max after replay was 40425. Duplicate `seller_id` breaks seller-level GMV. `silver_geolocation` is one row per zip. Duplicates would double-count when customers join to geo.

On gold, a duplicate `customer_sk`, `product_sk`, or `date_key` fans out `fct_order_items` and doubles that slice of revenue. Duplicate `order_item_key` doubles GMV. A null `price` zeroes that line in `SUM(price)`. An orphan `customer_sk`, `product_sk`, or `date_key` is dropped from a star-schema join, so dashboards understate revenue. `expect_table_row_count_to_equal_other_table` against non-quarantined `silver_order_items` tells me the gold inner join to orders dropped lines. After replay both sides were 105,024. The singular test `assert_gross_amount_equals_price_plus_freight` catches `gross_amount` drifting from `price + freight_value`. Finance "gross" would then disagree with the item grain. Two rows for one day on `fct_daily_sales` double that day's GMV on a time series. A null `revenue` disappears from `SUM` of daily revenue.

### Soda Core

Four local contracts. No Soda Cloud. `scripts/run_soda.py` writes `soda/ds_config.local.yml` (gitignored) with the warehouse path and runs `soda contract verify`. After the Phase 2 full-refresh I measured `fct_order_items` 105,024 rows, freshness 0.039 days, and `dim_customer` 89,505 rows.

| Check | Bound |
| --- | --- |
| `fct_order_items` `row_count` | 90,000–130,000 |
| `fct_order_items` `freshness(_ingested_at)` | < 7 days |
| `fct_daily_sales` `row_count` | 400–800 |
| `dim_customer` `row_count` | 70,000–110,000 |
| `silver_orders` `row_count` | 80,000–120,000 |
| `silver_orders` `freshness(_ingested_at)` | < 7 days |

If `fct_order_items` row count fails, gold is empty or a duplicated load roughly doubled GMV. After replay it was 105,024. Freshness uses `_ingested_at`, not `order_date`. 2018 dates would always look stale. If `fct_daily_sales` is outside 400–800, the daily spine collapsed or exploded. After replay it was 585. If `dim_customer` is outside 70,000–110,000, the person dimension is empty or duplicated. After replay it was 89,505. `silver_orders` after replay was 92,587. The orders freshness check is the same arrival clock as the dbt test, on the orders table.

## CI (Phase 3)

GitHub Actions is the merge gate. A pull request never sees `archive/`, bronze, or `onelake.duckdb`. It builds a committed seed fixture into `data/warehouse/ci.duckdb` and runs the checks that are about the code, not about the size or freshness of a live warehouse.

CI has no Kaggle dump and no ingest. `transform/seeds/` is a slice I sampled parents-first (`scripts/make_ci_seeds.py`): 2,000 orders, 2,253 items, 2,100 payments, 1,984 reviews, 2,000 customers, 1,715 products, 739 sellers. All six orphan checks were 0 when I wrote the slice.

`bronze_source()` reads `ref('<table>_seed')` when `ci_mode` is true, and bronze parquet otherwise. The `ci` profile target writes `ci.duckdb`, never the local warehouse. Seeds themselves are `enabled` only under `ci_mode`, so a normal local `dbt build` does not load fixture tables into `onelake.duckdb`.

Regenerate locally with `python scripts/make_ci_seeds.py --write` after ingest. Do not loosen full-scale bounds to make CI pass.

Volume tests encode full-warehouse counts and the measured review-score mean. They fail on a 2,000-order slice for the right reason, so CI excludes `tag:volume`. Freshness is an operational check on a live warehouse. Seeds carry a fixed `_ingested_at`, so a 7-day window would pass today and fail next week with no code change. That is why CI also excludes `tag:freshness`. Soda in CI checks gold column names and types. Column order is not enforced. Row-count and freshness contracts stay on the full warehouse.

| Check | CI (`--exclude tag:volume tag:freshness`) | Full warehouse |
| --- | --- | --- |
| Keys, accepted values, relationships, score 1–5, price/freight bounds, `gross_amount` | yes | yes |
| `expect_table_row_count_to_equal_other_table` on `fct_order_items` | no (`tag:volume`) | yes |
| `expect_column_mean_to_be_between` on `review_score` | no (`tag:volume`) | yes |
| `expect_row_values_to_have_recent_data` on `silver_orders._ingested_at` | no (`tag:freshness`) | yes |
| Soda gold schema (column presence and type) | yes (`scripts/run_soda.py --ci`) | no |
| Soda `row_count` contracts | no | yes (`scripts/run_soda.py`) |
| Soda freshness on `_ingested_at` | no | yes (`scripts/run_soda.py`) |

PR job (`.github/workflows/ci.yml`): sqlfluff, then

```text
dbt build --target ci --vars "{ci_mode: true}" --exclude tag:volume tag:freshness
```

then `python scripts/run_soda.py --ci`.

Push to `main` (`.github/workflows/main.yml`) runs the same `dbt build`, then `dbt docs generate`.

I proved the gate with a deliberate-bug PR. `assert_gross_amount_equals_price_plus_freight` FAILed 2253 and the merge button went red.

## Fabric (Phase 4)

I did not fork the models. `dev` (DuckDB), `ci` (DuckDB + seeds), and `fabric` (T-SQL) build from the same files. The claim is "repoint the profile", not "rewrite the project".

A Lakehouse SQL endpoint is read-only, so dbt cannot write T-SQL there. I split the work across two items in workspace `onelake-medallion-dev`. `lh_bronze` holds bronze Delta. `wh_onelake` holds silver and gold. `bronze_source()` on the fabric target reads `[lh_bronze].[dbo].[bronze_<table>]` from the Warehouse.

`pl_backfill_bronze` loaded history through the 2018-06-30 cutoff. Bronze `order_items` came out at 98,309, which matches the local backfill. 77 real Olist folders (2018-07-01 through 2018-10-17) are still sitting as the replay queue. I did not invent synthetic days. Landing dates are not contiguous. 634 folders span 2016-09-04 to 2018-10-17, and Olist has days with no orders. `last_batch_date + 1 day` would often point at a folder that does not exist, so the daily pipeline asks `meta.landing_batches` for the next real folder.

`pl_ingest_daily` copies the next unprocessed folder per table and advances that table's own cursor after its own copy succeeds. I first ran ForEach in parallel. Fabric Warehouse uses snapshot isolation. Five parallel UPDATEs to `ingest_control` aborted with an update conflict. So I made ForEach sequential. Each table still has its own cursor. If one copy fails, only that table stays behind.

`profiles.yml` has a `fabric` target with `authentication: CLI`. `dbt debug --target fabric` passes. The SQL dialect work is still in progress. After every Fabric fix I re-run `dbt build --full-refresh` on `dev`, because a change that fixes T-SQL and silently breaks DuckDB is the main risk. Fabric will hold fewer rows than dev until the replay queue is drained. That is expected. Compare Fabric against Fabric's own bronze.
